# Feedback on Nebius Token Factory and NVIDIA Nemotron

Written while building RuleSmith for the Nebius x NVIDIA Global AI Hackathon (October 2026). Specific, so it is actionable. Everything below was confirmed against the live APIs on 17 October 2026; the numbers come from `eval/results.md`.

## Nebius Token Factory

**What we used it for.** All inference: five pipeline stages across three Nemotron tiers through the OpenAI-compatible `chat/completions` endpoint with `response_format=json_schema`, `chat_template_kwargs.enable_thinking`, and `GET /v1/models` for runtime model resolution.

**What worked well.**
- Zero to hello world is genuinely fast: the OpenAI SDK with a changed `base_url` just works, and the `llms.txt` index of the docs is excellent for agents and humans alike.
- Having Lightning, Super and Ultra on one endpoint with one key made tiered routing trivial. Being able to say "Ultra for planning, Lightning for extraction, Super for the loop" and show the cost split per tier is a real product feature, not just a cost trick.
- The FAQ on the hackathon page and the hackathon Discord answered the "does my whole app need to run on Nebius" question clearly.

**What needs work.**
1. **Model ids are inconsistent across Nebius's own pages.** The Nemotron landing page shows `nvidia/Nemotron-3_5-Lightning` and `nvidia/Nemotron-3.5-Super-VL`, the cookbook shows `nvidia/nvidia-nemotron-3-nano-30b-a3b`, third-party integrations show `nvidia/nemotron-3-super-120b-a12b`. Mixed casing and separators (`3_5` vs `3.5`) mean copy-pasting from docs fails. We had to resolve ids case-insensitively against `/v1/models` at startup. One canonical id per model, printed everywhere, would remove a whole class of first-hour errors.
2. **The "Structured output & JSON" doc page has broken examples.** The Python `response_format` dict is missing commas, the cURL sample uses `"response format"` with a space, and the prose shows a `name/schema/strict` wrapper while the code passes a bare schema. We shipped a fallback chain (`json_schema` → `json_object` → prompt-only) because we could not tell from the docs which shape the server wants. Live result: the OpenAI-style `{"type": "json_schema", "json_schema": {"name", "schema", "strict": true}}` wrapper is accepted first time by Lightning, Super and Ultra, and the fallback never triggered. One correct example per SDK, plus a per-model "JSON mode" capability flag in `/v1/models?verbose=true`, would still save every builder an hour.
3. **Guided JSON decoding and long multi-line strings do not mix.** Our first design asked Nemotron for the Sigma rule as a YAML string inside a JSON field. Under `json_schema` mode about one authoring call in four and most refinement calls came back with YAML that did not parse: newlines dropped between keys (`service: sysmondetection:`), stray `}` at the end, list markers on the key line. Nested JSON objects never had this problem, so we moved the rule to a structured object and render YAML ourselves. A note in the structured-output docs ("keep string fields short; model nested data as objects") would steer people away from this.
4. **No published per-model support matrix for tool calling / JSON mode / reasoning toggle.** The docs say "look for the tag on the model card". That should be in the API.
5. **Rate-limit docs give no numbers** for the Startup tier. The adaptive window mechanism is well explained, but a table of starting RPM/TPM per tier would let builders size parallelism. We defaulted to 3 parallel rule authors blind.
6. **Fine-tuning does not list any Nemotron base model.** Re-checked on 18 October: the fine-tuning catalogue offers Llama 3.1/3.2/3.3, Qwen3, DeepSeek-V3 and gpt-oss, no Nemotron. Distilling our validator-approved Super rules into a Lightning/Nano fine-tune is the obvious next step for cost (the validator produces execution-verified training pairs for free), and it is not possible on the platform today. We got most of the first-draft gain another way, by retrieving three SigmaHQ rules per logsource and technique into the author prompt; a Nemotron LoRA on the same corpus would make that a product feature.
7. **Sandboxes are gated behind an access request.** For a hackathon whose Coding track says "write, run and test code in Token Factory", open self-serve access during the event would have let us run pySigma validation inside Token Factory instead of in-process.

**Would we build with it again?** Yes. The economics of Lightning for extraction (effectively free at $0.06/M input) and Ultra only where judgement matters are hard to beat, and the OpenAI compatibility meant zero vendor-specific code outside `llm.py`.

## NVIDIA Nemotron

**What we used.** Nemotron 3.5 Lightning (extraction), Nemotron 3 Super (authoring and refinement), Nemotron 3 Ultra (planning and red-team).

**What worked well.**
- Reasoning on/off via `chat_template_kwargs.enable_thinking` is exactly the right control for an agent that mixes judgement stages with extraction stages. The model cards document it clearly, including the client-side budget pattern. Live: Ultra with thinking answered the smoke test in under 5 s with an 800-token trace that never leaked into `content`.
- Lightning's 1M context means we never chunk a report, and at 185 input tokens the smoke test cost $0.00002 with 0.5 s latency.
- The model cards give concrete sampling recommendations (temp 1.0/top_p 0.95; 0.6 for tool calling on Nano). We used them.
- Super writes Sigma that pySigma accepts: once the rule travelled as a JSON object, the only parse failures left were Sigma semantics (an unknown modifier, a field test written inside `condition`), which the validator reports and the refine stage fixes.

**What needs work.**
1. **Reasoning traces leaking into `content`.** Depending on the serving stack, a `<think>` block can arrive inline, be split into `reasoning_content`, or be truncated when `max_tokens` is hit. We strip `<think>` defensively. A guarantee that `content` never contains the trace when `enable_thinking` is on would simplify every structured-output client.
2. **The tool-call format is documented only by parser name** (`qwen3_coder`), not by the token-level format. Builders who cannot use vLLM's parser have to reverse-engineer it.
3. **Lightning does not know ATT&CK ids without thinking.** Asked to map `rundll32 comsvcs.dll MiniDump lsass` to a technique, Lightning (thinking off) answered T1059.005, T1005, T1059 and the retired T1067 on four runs; with thinking on it answered T1003.003. Super and Ultra answered T1003.001/T1003 every time. For extraction we keep Lightning for speed and let the validator check every id against the ATT&CK index, but the fast tier should not be trusted with taxonomy lookups. A small ATT&CK-aware fine-tune of Lightning would be a cheap "Nemotron for security" win.
4. **Backslashes and defanged indicators.** In JSON output Super regularly double-escapes Windows paths (`"C:\\\\Windows"`) in test events while writing the rule with single escapes, so its own positive tests never matched; the refine stage then "fixed" the tests three times in a row without noticing. It also copies defanged domains (`quietledger[.]net`) from the report straight into rules. Both are now normalised deterministically before validation. Worth a line in the model card's structured-output guidance.
5. **Rule/test consistency.** The most common remaining failure is a rule that requires a field its own positive events do not carry (`Protocol: tcp` in the rule, no `Protocol` in the events). Telling the model, per named selection, which one failed and which field was missing (`selection_proto=NO MATCH (event lacks Protocol)`) is what finally made the refine loop converge; a bare "positive test P1 did not match" was not enough for Super.
6. **Super writes correlations as single rules.** For every "sequence" behaviour (CreateUser then CreateAccessKey then AttachUserPolicy; a burst of 4625 followed by 4624; vssadmin, bcdedit and wbadmin in a row) Super ANDs the steps into one Sigma rule, sometimes with an invented `timeframe`/`count()` block. No single event can satisfy it, so the rule can never fire, and the model does not notice from "positive test did not match". A lint that names the contradiction (`selection_vss wants Image|endswith=\\vssadmin.exe, selection_bcd wants Image|endswith=\\bcdedit.exe; one event cannot satisfy both`) plus an explicit "one rule matches one event" line in the prompt fixed most of it. Sigma correlation rules exist for exactly this; a Nemotron that knew the difference would be a real step up for detection engineering.
7. **Sigma specifics**: hallucinated modifiers (`|not contains`, `|windash` on a hostname), a field test inside `condition`, and a Sysmon `UserAgent` field that does not exist were the recurring Sigma slips. The validator exists precisely because this is where general-purpose models slip; a Nemotron fine-tune on SigmaHQ-style rules would be a natural release.

**Would we build with it again?** Yes. Being able to show judges three open-weight models from one family doing three different jobs, with the same prompt conventions, is a strong story for open infrastructure.

## Tavily

`extract` with `extract_depth="advanced"` and markdown output was the difference between usable report text and HTML soup (live: the MITRE T1003.001 page came back as clean markdown in one call); `search` with `time_range` made "find me the latest reporting on X" a one-liner. Documentation inconsistency spotted: the Python reference documents `map` while an example calls `mapping`, and `crawl`/`map` take `instructions` in the reference but `query` in the quickstart.
